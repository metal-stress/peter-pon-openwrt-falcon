01The stick

A whole fibre modem in an SFP cage.

The Huawei MA5671A is a complete GPON terminal, an ONT, built into an SFP module. Fibre goes in one end. The other end goes into your router's SFP cage, and the module takes the place of the operator's box.

It is also a computer: a FALC ON system-on-chip with a MIPS 34Kc core, 64 MB of RAM and 16 MB of flash. It runs Linux. Until now, a very old one.

Peter-Pon is what it runs instead: OpenWrt main on Linux 6.18.55 with musl, the GPON drivers updated for that kernel, an OMCI engine of its own, its own tools and web pages.

03Why it exists

Stuck in 2014.

The stock firmware is OpenWrt 14.07 on Linux 3.10.49 with uClibc 0.9.33. Upstream OpenWrt boots on the chip but carries no GPON drivers, so the firmwares we started from stayed on the old kernel.

Peter-Pon moves the whole stack to today's OpenWrt, and then keeps going.

What the stock firmware left on the table

  • One CPU for Linux. The second virtual processor ran a small EEPROM program that never sleeps.
  • A quarter of the instruction cache for Linux. One 8 KiB way of 32 KiB.
  • Flash read four bytes per command.
  • After a watchdog reset, no record of why.
  • No way to read the flash chip's own health.

04The set-up

Type the identity. It does the rest.

A GPON line is run over OMCI. The operator's OLT questions whatever sits at the end of the fibre, then decides which services to set up, and how.

Peter-Pon's own OMCI engine answers the way the ONT your operator expects would answer, from a library of 91 devices in eight OMCI software families. You type the identity; the engine works out the rest.

The ONU Configuration page lays that out as three steps, left to right, from the operator to your router. Each step shows where it stands.

  1. AuthenticationThe serial number, and the password or LOID if your line uses one. This is the part you type.
  2. What the OLT seesThe ONT model the module answers as. Automatic picks it from the library; Expert mode lets you open it up and change it.
  3. DeliveryEvery service the OLT sets up, as one lane to your router. Click a lane's router side to change how that service arrives.

Diagram The strip across the top of the ONU Configuration page, redrawn. The recordings below are the page itself.

Every service goes to the router

Internet, TV, voice: whatever the OLT provisions is delivered to the router's port the way the OLT configured it. Nothing ends on the stick.

The Connection page draws one coloured lane per service: the operator's VLAN on the left, what the router gets on the right, what the module does in between. Five steps from light to traffic, and a plain sentence when one of them fails.

Behind that sentence is an assistant with 39 stage codes and 32 findings. Most people will only ever see “Fibre link up”.

05 – 07The hardware

Same silicon. More machine.

Nothing was added to the board. A second virtual processor, three quarters of the instruction cache and a faster flash bus were in the chip all along.

Each change in the next three chapters was measured before and after. Flip the switches yourself.

05The second CPU

We got a CPU back.

The 34Kc has two virtual processors and four hardware thread contexts. The stock firmware ran Linux on one. The other ran its SFP EEPROM program: about 900 instructions in a loop with no wait, answering the router's I2C reads, because the stick has no EEPROM chip and the chip has to play one.

The project owner's instruction, verbatim: “our firmware goes to eleven. this means SMP”.

So the EEPROM emulation was rewritten as our own engine and moved to a spare thread context, where it sleeps until the router reads. The freed virtual processor became Linux's second CPU. The kernel says so at boot: smp: Brought up 1 node, 2 CPUs.

One catch. The GPON drivers were written for one CPU. So they run only on CPU0, an island: every entry point is pinned there, an automatic check stops the build if a new one is not, and a runtime tripwire counts violations. CPU1 runs everything else.

06The cache

Linux was living in a quarter of the cache.

The L1 instruction cache is 32 KiB in four ways of 8 KiB, and it can be split between the two virtual processors. On the stock firmware the split meant for the EEPROM program landed on the side that runs Linux, and Linux ran from one way.

We found it by reading the register back, and a cache benchmark put the knee at 8 KiB. First fix: three ways. Second: all four, shared.

And while we were in there

  • 16 KiB pagesNo more data-cache aliasing; fork, exec and page faults about 1.4 to 5 times cheaper. It costs 8 to 12 MiB of available memory.
  • EROFS rootReads 25 % faster than the xz squashfs it replaced.
  • RAM given backStock hid 1 MiB from Linux for the EEPROM program. Now 16 KiB stays hidden.
  • A crash record64 KiB of RAM that survives the watchdog reset: the last console lines are still there after the reboot.
  • A web UI that loadsLuCI's cold load, 41 requests: 5.77 s to 1.66 s.

07The flash, and the boot

100 MHz, four lines. Then we raced it.

The stock driver reads the flash four bytes per command at 50 MHz: 2,335 KiB/s. Peter-Pon reads it through the SPI controller's memory-mapped window, at 100 MHz, on four data lines. The boot loader got the same clock, and loads the kernel in 1.56 s instead of 3.68.

A modern kernel is heavier than a 2014 one: on this chip a system call, a fork or an exec cost 1.7 to 2 times what they did on 3.10. The work in these three chapters is part of how the boot still ended up shorter.

      08The controls

      Nothing on this device is out of reach.

      Peter-Pon gives you the whole machine, with a label on every control and a lock on the ones that can strand it.

      Twelve pages of its own in LuCI, in Simple and Expert modes, on five themes, in English with five more languages as packages. One static program, omng, that holds every tool. And a logger whose brief was three words long: “we want everything”.

      The OMCI database entity by entity, the queues and shapers the OLT set up, the flash chip's own health registers, the firmware slot you are not running: each has a page or a command. Click any screen on this page to see it larger.

      • Real page, example data The MIB explorer runs on the MIB module's own test document; the QoS section and the stills run on a simulated unit or on test fixtures. The entities, ports and rates on them are examples.

      The flash, looked after

      Sixteen megabytes hold the boot loader, its settings with the unit's calibration, and two firmware slots. GPON › Flash shows them as a map and lets you act on each part.

      • Health check. Reads the flash chip's own status and error-correction registers, read only: the part and its identity, bit errors it corrected, a program or erase failure it latched.
      • Data check. Scans the partitions for bit errors, checks each firmware slot (kernel checksum, root filesystem, release, packages) and compares the two slots.
      • Copy, resize, back up. Copy the running firmware to the other slot as a fallback, change the split between the two slots or use one large slot, and download a backup of the whole chip.

      The OpenWrt way

      • Every setting lives in UCI. /etc/config/gpon, sfp_eeprom, network: LuCI, the shell and the AI agent all change the same options.
      • One rule per option. Each option has one format and range, checked the same way by LuCI, the command line, the boot and the agent.
      • OpenWrt's own plumbing. The web backend is ucode and rpcd over ubus, services run under procd, and the OMCI daemon answers on ubus too.
      • A normal OpenWrt build. Clone OpenWrt, add the overlay, make menuconfig, make. A sysupgrade keeps your settings.
      # uci set gpon.ui.expert='1'
# uci set gpon.onu.mc_vlan='40'

      09The AI agent API

      It talks to AI agents. Carefully.

      Some owners will never open a settings page. They will ask an assistant. So the stick carries an API written for one, and a reference the agent reads from the module itself.

      It is off until you switch it on, has its own login, and switches itself off after 24 hours idle.

      Every change is a trial. It reverts by itself unless it is confirmed. The one-way doors (the laser calibration, the boot loader, which slot boots) are refused, or need a flag the agent may pass only after you agree.

      10Telemetry out

      Read-only, for your dashboards.

      A second key, for monitoring. It may call one read-only method and nothing else, so it is safe to hand to Home Assistant or any other monitoring tool; the Home Assistant recipe is on the page and in the reference on the module.

      One answer carries the PON state, the optics, the link, the error counters, a minute of traffic and the services.

      It never carries the serial number (only its four-letter maker prefix), the passwords, the LOID, the MAC address or the calibration.

      11The receipts

      Eleven is the part you can check.

      Loud claims are cheap. This project keeps receipts. No image is released until every automatic check passes, and a check that cannot run counts as a failure. Mutation tests break the code on purpose to prove the tests notice.

      ~330automatic checks an image must pass before it is released.
      213behaviour and mutation test runs, plus 41 quick checks, for r681.
      5thattempt on which r681 passed. The first four were refused on bookkeeping faults.
      857written specs.
      426documented tools, their limitations included.
      3,258commits since 2026-09-03.
      1. Every difference has a written reason.The GPON drivers were updated to run on Linux 6.18. Wherever they behave differently from the original, the difference is in a register with its reason: a decision, never a mystery.
      2. Vacuous is not a pass.A check that cannot tell “no signal” from “not measuring” reports a broken probe, never a verdict.
      3. Tested on real fibre.Reports from testers on real fibre lines: 88 report folders since the first run on 2026-09-12, a few of them the developer's own notes and runs.
      • Counted The automatic checks are the numbered sections of the release script; the test runs and quick checks are those of the r681 release. Its mutation tests alone took 7,414 seconds.
      • For example That first fibre run dropped the session every 18 seconds or so. The cause was ours: one interrupt handler where the original driver has two. It was split again, and an automatic check now stops the build if anyone merges it back.
